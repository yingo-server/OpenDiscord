# V2-1 写入路径批量化实现规格（基于只读审计）

状态：规格草案 · 依据：v2.0-roadmap 写入路径审计（job 05bdf4b1）
本文件是给实现 Agent 的锚点：明确改哪些函数、守住哪些语义、如何验收。

## 根因（一句话）
每条 msg_send 在 dispatch goroutine 内同步执行一次 `AllocateSeq`（独立 SQLite 写事务，
`UPDATE conv_seq ... RETURNING`），与 flusher 的 group-commit 批事务争同一写锁
（`_txlock=immediate`），把批处理收益完全抵消 → msg_send ACK 崩塌。

## 改动面（最小切口，按依赖顺序）

### 1. store 层：seq 分配并入消息批事务
- `server/internal/data/store/api.go`：`MsgWriter` 接口新增/改造为支持「一次事务内
  UPDATE conv_seq（按 cid 预留 N 个 seq）+ INSERT 多条 pending msg」。保留原
  `AllocateSeq` 供兼容/回滚路径，新增 `AppendWithSeq` 类方法（命名由实现定）。
- `server/internal/data/store/sqlite/msgwriter.go`：实现该方法——单个事务内先按 cid
  取出当前 seq 并预留 len(batch) 个，再批量 INSERT，每条 pending msg 带分配好的 seq；
  事务提交后返回 (msg_id, seq) 列表供 ACK。**同 cid 严格单调、不重叠**。
- 守住：durability 不变（ACK 仍只在事务 commit 成功后发）。

### 2. pipe 层：onMsgSend 不同步分配 seq，flusher 聚批
- `server/internal/data/pipe/pipe.go`：`onMsgSend` 不再调 `seq.assign`/`AllocateSeq`；
  只做 dedup + 成员校验 + 入 writeCh（携带 client_msg_id）。
- `server/internal/data/pipe/flusher.go`：`flush` 时按 cid 把批内消息分组，每组调用
  步骤 1 的新方法；用返回的 seq 列表回填 msg.Seq、dedup.Remember、emit(ACK)。
- 守住：批内多 cid 各自预留段、互不干扰；单 cid 顺序由 writeCh FIFO 保证。

### 3. 配套（同批或紧随）
- `config/policy.json` + `policy/types.go`：`write_path.batch_size` 默认 1000→500
  （审计引 docs/perf-sqlite-write-path.md：batch=500 p95≈70ms vs 1000≈187ms）。
  这是配置默认改动，不是门槛改动。
- `dedup` 批内隔离：flusher 遇单条重复不应整批 500；改用 INSERT OR IGNORE + 事后按
  client_msg_id 回读已存在行，回放其 (msg_id, seq) 给该条 ACK（不连坐其它消息）。
- `fanoutNew` 从 flusher goroutine 解耦到独立 fanout 队列（若步骤 1/2 后仍是瓶颈）：
  已有 fanoutPlane 可承接，按批投递而非逐成员同步 env 构造。

## 明确不做（本批）
- 不 ACK 前移（不在事务未提交时 ACK，除非单独定义 durability 降级并声明）。
- 不做分片（V2-2）；不改协议/chat.proto；不改网关转发层（conv_id 不可见）。
- 不改限流/容量契约（V2-0 负责）。

## 验收（CI 压测，不伪造）
- 正确性：go test -race 全绿；dedup 幂等单测（重复客户端消息回放原 ACK）；
  seq 单调单测（同 cid 连续 N 条 seq 严格递增不重叠）；durability（commit 失败无 ACK）。
- 性能：CI 跑 S-2（1000×50）对比 v1.5 基线 16.38%，中间目标 ≥60%；记录真实数字，
  不达标就如实报告，不调门槛。
- 回归：S-3（512×10）不低于 v1.5 的 93.86%（允许测量抖动 ±1%）。
