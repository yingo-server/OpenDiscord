## L1 低风险、中高收益（不动核心架构，1-2 版本可完成）

### L1-1 dedup 批内隔离
机制：当前批内一条 `ErrDuplicate` 整批 500；改为 `INSERT OR IGNORE` + 事后按 client_msg_id 回读回放原 ACK，只影响重复条自身。
收益：【推测】raw ceiling 下重复请求比例高时，减少整批回滚→吞吐 +10~30%。
风险：低。工作量：小。文件域：store/sqlite + flusher。

### L1-2 扇出解耦出 flusher goroutine
机制：`fanoutNew`（500 人逐成员 env 构造 + putBulk）当前在 flusher goroutine 内同步执行，拖慢下一批 commit。迁到已有 `fanoutPlane` 的独立 goroutine，按批投递。
收益：【推测】flusher 提交间隔缩短→ACK 延迟 -20~40%；大群场景更明显。
风险：中（需保证消息落库后才扇出、顺序不丢）。工作量：中。

### L1-3 ACK 入队即发 + 持久化队列（durability 降级）
机制：ACK 在消息进入内存 WAL 环形缓冲时即返回，后台单 writer 批量刷盘；崩溃窗口用 WAL replay 恢复。durability 从"已落库"降为"已进持久化队列"。
收益：【理论】ACK 延迟从 commit  bound 降到内存 bound，吞吐可提升 2~5×。
风险：**高**（语义变更，需客户端/协议声明；崩溃窗口数据丢失风险）。工作量：大。

### L1-4 SQLite PRAGMA 深度调优
机制：`synchronous=OFF`（WAL 下掉电丢最近事务）、`wal_autocheckpoint` 调大、`mmap_size`、`temp_store=MEMORY`、`cache_size` 加大、`journal_size_limit`。
收益：【推测】10~30%（当前 NORMAL 已较优，OFF 有风险）。
风险：中（掉电数据丢失面扩大）。工作量：小。

### L1-5 消息体压缩 / 精简 wire
机制：msg_send payload 用二进制（msgpack/protobuf）替代 JSON；批量帧（一次 WS frame 带多条消息确认）。
收益：【理论】带宽 -40~60%，CPU 编解码 -20%，高连接数场景有效。
风险：中（协议兼容）。工作量：中。

## L2 架构级（数量级收益，需 1-2 个大版本）

### L2-1 热库按 conv_id 分片（K 个 SQLite 文件 + K 写者）★核心
机制：store 层 shard router，按 cid 哈希到 K 个独立 SQLite 文件，每个文件独立写锁 + writer goroutine。conv/identity/media/sys/mailbox 留全局库。
收益：【理论】写吞吐 ×K（4 分片≈4×，8≈8×）；直接突破单写者天花板。
风险：高（跨 shard 事务、seq 单调、dedup 跨进程、管理面 messages/search 聚合重写）。工作量：很大。

### L2-2 会话 Actor 模型
机制：每个活跃会话一个 goroutine 独占 seq 分配 + 成员表 + 水位线状态 + fanout 决策；消息进 Actor mailbox 串行处理，无锁。Actor 按 cid 分片部署。
收益：【理论】消除所有跨 goroutine 锁竞争 + 缓存局部性提升，吞吐 ×2~5×。
风险：高（Actor 生命周期、迁移/恢复、与分片协同）。工作量：很大。

### L2-3 写路径彻底异步化（完全解耦 ACK 与 DB）
机制：消息进无锁 MPSC 队列 → 独立 writer pool 批量落库；ACK 立即返回（带"已接收"语义）；客户端靠 MSG_ACK 状态机 + 重传保证最终一致。
收益：【理论】ACK 延迟降至微秒级，吞吐取决于 writer pool 数量。
风险：高（语义降级、重传风暴、乱序）。工作量：很大。

### L2-4 冷热分层深化（热库只留活跃窗口）
机制：热库只保留 N 分钟消息，其余异步移到冷库（PG/对象存储）；查询走统一视图。减小热库 B-tree 尺寸→写放大降低。
收益：【理论】SQLite 写放大 -30~50%（B-tree 更小、checkpoint 更快）。
风险：中（冷库依赖变强、查询延迟）。工作量：中。

### L2-5 普遍拉取完成态（服务端零逐成员扇出）
机制：服务端只维护每会话 latestSeq + 发一条 watermark（O(1)），客户端 pull-scheduler 按 seq 批量拉；彻底取消 102 逐成员帧（v1.4 已铺路但未完成）。对于 500 人群，下行帧从 500 条/msg → 1 条/批。
收益：【理论】大群下行帧量 -99%；服务端 fanout CPU/内存 -90%；这是 v1.4 已识别但未彻底完成的路线。
风险：中（客户端拉取收敛延迟、离线成员靠 SYNC 补拉）。工作量：中。

### L2-6 多进程 / 多实例水平扩展
机制：无状态网关 + 独立消息集群，按会话哈希路由；一致性哈希 + 会话粘滞；跨实例用 NATS/Redis 总线。
收益：【理论】吞吐线性 ×实例数；突破单机 CPU/内存/IO 上限。
风险：**极高**（分布式一致性、会话迁移、跨实例 dedup/seq、部署复杂度）。工作量：巨大。违反"无 Docker/单机"原始约束，需用户确认。

### L2-7 读写分离（只读副本）
机制：主库写，N 个只读副本服务 920/8 历史拉取 + 管理面查询，减轻主库读锁竞争（审计实测读并发让批写慢 3×）。
收益：【理论】写吞吐 +50~100%（消除读锁干扰）。
风险：中（复制延迟、最终一致）。工作量：中。需 SQLite  Streaming 或 PG 主从。

## L3 激进重构（理论极限，工程量大，谨慎）

### L3-1 替换 SQLite 为专用时序/消息存储
机制：自研 append-only 日志存储（类 Kafka）：消息顺序写文件 + 稀疏索引 + mmap 读；无 B-tree 更新、无写放大。
收益：【理论】写吞吐 ×5~20×（顺序追加 vs B-tree 随机写）。
风险：极高（重写整个 store 接口、查询模型变化）。工作量：巨大。

### L3-2 LSM-Tree 存储（RocksDB / Pebble）
机制：用 LSM 替代 B-tree，写先入 memtable + WAL，后台 compact；写吞吐天然高。
收益：【理论】写吞吐 ×3~10×（LSM 顺序写特性）。
风险：高（CGO 依赖、compaction 抖动、查询语义适配）。工作量：大。

### L3-3 全栈 Actor / CRDT
机制：服务端 Actor + 客户端本地优先（Local-first），消息用 CRDT 合并，离线写不阻塞；服务端只做同步骨干。
收益：【理论】端到端延迟降至本地、服务端压力大幅下降；架构完全不同。
风险：极高（产品语义重写、客户端复杂度爆炸）。工作量：巨大。

### L3-4 eBPF / io_uring 加速网络与磁盘路径
机制：WS 收发用 io_uring 批量 syscall；连接路由用 eBPF 在内核层分流。
收益：【推测】网络/IO 密集场景 -10~20% CPU。
风险：高（平台绑定 Linux 5.x+、代码不可移植）。工作量：大。

### L3-5 列式存储 + 向量化查询（分析型负载）
机制：管理面消息搜索/审计走列存（ClickHouse/DuckDB），热库只服务 OLTP。
收益：【理论】管理面查询 ×10~100×，间接释放热库读压力。
风险：中（新增组件、运维复杂）。工作量：中。

## L4 部署/硬件层（不改代码）

### L4-1 更快的磁盘（NVMe / 内存盘）
收益：【推测】SQLite fsync 延迟 -50~90%，直接提升 commit 吞吐。零代码改动。

### L4-2 更大页缓存 / 内存
收益：热库全驻内存 → 读延迟趋零，写 checkpoint 更快。

### L4-3 多机 + 负载均衡
收益：线性扩展，但需 L2-6 架构支持。

## 最终决策（2026-11-21 晚）
用户选择自研 append-only 日志为主线，但两次 CI A/B 压测（283/s、174/s）远低于
SQLite（1197/s），主线不成立，**用户决定彻底放弃自研**。appendlog 引擎及接线代码
已全部删除，生产保持 SQLite 唯一路径，稳定版 v2.0.0。
**以下清单为历史脑暴记录**：L3-1/L3-2 等存储替换路线已否决；L2-6 多机违反单机约束；
L3-3/4/5 单机收益存疑。仍具参考价值的低风险项：L1-2 扇出解耦（ACK 已在 fanout 前发出，收益有限）。

### L2-5 普遍拉取完成态：已实测，收益不成立（2026-11-21）
首次让压测客户端真正上报 CLIENT_CAPS(18) 并走 watermark 路径（此前 stressd 从未
上报能力，所有 universal_pull 压测实际测的是 inline 102 legacy 路径）。顺带修复了
由此暴露的 stressd WS 并发写 panic（sendSync vs doOp，加 writeMu）。
真实 S-2 4c16g 数据（run 44907652962）：
- 可用性 13.66%（inline 基线 17.54%，**下降**）；ACK 945/s（基线 1197/s，下降）
- server_drop 12011（基线 85188，**-86%**，服务端扇出压力确实大幅降低）
- watermark 932/s、SYNC 931/s、msg_new 82989/s、收敛 p95 1479ms
**结论**：普遍拉取把帧量从"服务端主动 push"转成"客户端 SYNC 拉取回放"
（931 SYNC/s × ~89 条/次 = 82989 个 102 帧），总帧量未减少，只是转移；额外拉取
往返延迟使端到端可用性略降。根因是现有协议下 SYNC 逐条返回 102（每消息一个
Envelope），无法合批——正是 perf-postmortem 已证伪的"真合批"路线（protobuf wire
非自描述、多 Envelope 拼接字段覆盖）。**L2-5 在现有协议下无法达成 O(1) 下行，
不加新协议则不继续**。服务端减负（-86% drop）是真实收益，但不转化为可用性。

## 已决策路线（2026-11-21，历史）
- **存储主线：L3-1 自研 append-only 日志**（类 Kafka 顺序写 + 稀疏索引），替代 SQLite
  作为消息热存储；放弃互斥的 L2-1 分片与 L3-2 LSM。
- **约束：保持单机 / 无 Docker**——跳过 L2-6 多进程水平扩展；L4 硬件项仅文档不改代码。
- **节奏：全部逐项实现**——L1 全套（可与任何存储兼容）→ L3-1 核心引擎 → 依赖它的
  L2/L3 项，每项一个小版本 + CI 验证 + 真实压测数字，不调门槛不伪造。
- 具体顺序见 memory 2026-11-21「架构全量实现决策」。

## 推荐路线（历史建议，已被上述决策取代）
1. **L1-1 + L1-2**（低风险、可快速落地，预估 +20~40% 综合吞吐）
2. **L2-5 普遍拉取完成态**（v1.4 已铺路，大群下行帧 -99%，收益/风险比最优）
3. **L2-1 分片**（数量级写吞吐提升，但是真正的硬骨头）
4. **L2-7 读写分离**（中风险 +50~100%）
5. 若还不够 → L2-6 多实例 或 L3-1/2 换存储引擎

**诚实底线**：当前 17.54% vs 门槛 90% 的差距，L1 级优化补不上；需要 L2 架构级改动才可能数量级突破。不违反客观规律，不通过改门槛达标。
