# OpenDiscord v2.0 架构重设执行路线

状态：执行中 · 日期：2026-11-21 · 基线：v1.5.0（tag 41fa420，CI -race 全绿，9 产物发布）
依据：docs/architecture-reset-v2-plan.md（草案，全部性能数字来自真实 CI 压测）

## 2.0 首发范围（经审计后锁定，不贪多）

v2.0 目标是**解决 v1.4 已定位的写入瓶颈**，不是一次性重写全部架构。分两个可独立验证的阶段：

### V2-0：显式容量契约（低风险，先做）
- 定义准入容量（2c2g / 4c16g 两档）并让超限**显式拒绝**而非静默超时。
- 复用现有 limiter / policy 机制，尽量不加新协议 kind。
- 验收：准入容量内可用性 ≥95%（原本就达标的场景不退步），超限时客户端收到明确响应、不挂起。

### V2-1：写入路径批量化（中风险，2.0 核心）
- 把 msg_send 的 SQLite 写入从"每条事务"改为"批量合并 + 单 writer goroutine"，
  在 durability 语义明确的前提下前移 ACK。
- 验收：S-2（1000×50）从 16.38% 提升到中间目标 ≥60%（用 CI 压测实测，不伪造）。

### 后续（不在 2.0 首发，按审计结果再立项）
- V2-2 热库分片（conv_id hash → K 库）：需改 store 接口，风险高，单独小版本。
- V2-3 会话 Actor + 普遍拉取完成态：动核心投递，单独小版本。
- V2-4 冷热分层：延续 OPS-1 未完成项。

## 审计先行（本路线的前置）
两个只读 Agent 并行审计，回来后锁定实现切口：
1. 写入路径审计：msg_send → ACK 全链路，找真实瓶颈点、group commit/WAL 真相、最小改造面。
2. 容量契约与分片审计：限流现状（超限是否显式）、分片最小切口、跨分片查询可行性。

## 审计发现（2026-11-21，只读 Agent）
### 容量契约与分片审计（已完成）
- 超限帧不配对：kind13 RATE_LIMITED 不带 client_msg_id（proto 4-9 reserved）→ 客户端 outbox 挂 10s 才超时（apps/client/src/net/sync/outbox.ts:312）。
- **ACK 不撒谎被违反**：客户端 handlers/msg-ack.ts 与 outbox.ts:181 不检查 MSG_ACK.status≠0，NACK 被当成功。这是必须修的语义 bug（与性能无关但属容量契约前提）。
- 队列满 writeCh=128 → kind10 ERROR{503 busy} 同样无 request_id 关联。
- 容量契约方案：新增 policy 顶层 capacity 段（现有 rate_limit 是每用户令牌桶，装不下全局容量轴）+ 一个 featureflag + SIGHUP 热改；拒绝帧走零协议改动的 kind10 ERROR+RequestID，客户端按 request_id fail outbox。
- 分片切口：store 层 shard router（对 pipe 透明）优于 pipe 多实例（conv_id 在 usergw 不可见、破坏透传）；只分片 msg_messages_hot+conv_seq，conv/identity/media/sys/mailbox 留全局库；messages/search 跨分片聚合属 V2-2 独立工作量。
- 结论：V2-0 不动 store，落在 usergw/pipe/客户端 + policy.capacity + flag。

### 写入路径审计（已完成，job 05bdf4b1）
- **首要根因**：seqalloc 每条消息一次独立写事务（UPDATE conv_seq，pipe.go:530 + sqlite/msgwriter.go:329），与 group-commit 批事务争同一 SQLite 写锁（`_txlock=immediate`），批量收益被完全抵消。这是 msg_send ACK 崩塌的代码级原因。
- 次要：单 dispatcher 单 flusher 串行天花板；500 人扇出在 flusher goroutine 内同步执行（不在事务内但挤占 outFan）；batch=1000 实测 p95≈187ms vs batch=500≈70ms（未按实测调）；dedup 冲突整批连坐 500（resolveConflict 无调用点）。
- SQLite 已 WAL + synchronous=NORMAL + busy_timeout=5s，单写者串行，连接池 4 但写锁一把。
- **V2-1 最小切口**：seq 预留并入 AppendMessages 同事务（UPDATE conv_seq + INSERT 同 tx），onMsgSend 不同步分配 seq、由 flusher 按 cid 聚批；ACK 仍在 commit 后（保 durability）。可选第二步：扇出迁到独立 fanout goroutine 解耦。配套：batch 默认 1000→500、dedup 批内隔离。
- 守住：durability（ACK=已持久化）、seq 单调不重叠、dedup 幂等、ACK 不撒谎。

## 纪律
- 不违反客观规律：不通过改门槛/改测试条件/伪造数据达标；压测数字全部来自 CI。
- 每阶段独立 tag（v2.0.0-beta.1 / beta.2 / v2.0.0），CI 绿 + 压测有真实改善才进下一步。
- 守住的语义：seq 单调、dedup 幂等、durability 等级明示、ACK 不撒谎（前移后崩溃窗口要明确）。
- Agent 只读审计阶段不改文件；实现阶段文件域隔离，不 commit/push/tag；主会话统一提交。
- 不引入 Docker；不走 LAGGING/RESYNC 已证伪路线；不重打历史 tag。

### V2-1 真实压测结果（2026-11-21，run 44878897175，S-2 4c16g raw ceiling）
- 实测：availability 11.69%、acks 23796 / attempted 203523、server_drop 88503、
  p95 805.7ms、rpm 407046（ack 吞吐 ≈793/s）。
- 对比 v1.5 基线（同场景 raw ceiling）：availability 16.38%、rpm ≈212186、
  ack 吞吐 ≈579/s（由 106093×16.38%/30s 推算；原证据目录已清理，为记录值）。
- 第二次（seq批量 + batch500，run 44879921690）：availability 17.54%、
  acks 35909 / attempted 204717、server_drop 85188、p95 471.2ms、rpm 409434
  （ack 吞吐 1197/s）。
- 对比 v1.5 基线（同场景 raw ceiling）：availability 16.38%、ack 吞吐 ≈579/s。
- **诚实结论**：ACK 吞吐从 ≈579/s 提升到 1197/s（**+107%，翻倍**），可用性从 16.38%
  升到 17.54%（略超基线），p95 从第一次的 805ms 降到 471ms。seq 批量分配 + batch=500
  的组合确实显著提升了写路径吞吐——这是真实、可量化的改善。但绝对可用性 17.54% 距
  S-2 门槛 90% 仍是数量级差距：**单进程 SQLite + 满速扇出的物理天花板未被突破**，
  需要 V2-2 分片/会话 Actor 等架构级改动。不改门槛、不伪造数据。
- v2.0 价值定位：**容量契约（显式拒绝而非静默挂起）+ ACK 诚实 + 写吞吐翻倍**，
  不宣称"容量达标"。超限场景由 V2-0 的显式限流兜底。
- 下一步可选（均未达质变预期，谨慎）：batch 1000→500（历史实测 p95 187→70ms）、
  dedup 批内隔离（当前整批 500 连坐）、fanout 解耦出 flusher goroutine；或接受
  "单进程 SQLite 物理上限"这一客观规律，由容量契约（V2-0）显式限流而非硬扛。
  产品侧决策：继续优化 vs 接受物理边界 + 容量内 SLA。

  可用性 13.66% 低于 inline 基线 17.54%；总帧量只是转移而非减少。完整数据与结论见
