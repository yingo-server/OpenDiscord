# OpenDiscord v2.0 架构重设执行路线

状态：执行中 · 日期：2026-11-21 · 基线：v1.5.0（tag 41fa420，CI -race 全绿，9 产物发布）
依据：docs/architecture-reset-v2-plan.md（草案，全部性能数字来自真实 CI 压测）

## 2.0 首发范围（经审计后锁定，不贪多）

v2.0 目标是**解决 v1.4 已定位的写入瓶颈**，不是一次性重写全部架构。分两个可独立验证的阶段：

### V2-0：显式容量契约（低风险，先做）
- 定义准入容量（2c2g / 4c16g 两档）并让超限**显式拒绝**而非静默超时。
- 复用现有 limiter / policy 机制，尽量不加新协议 kind。
- 验收：准入容量内可用性 ≥95%（原本就达标的场景不退步），超限时客户端收到明确响应、不挂起。

### V2-1：写入路径批量化（中风险，2.0 核心）
- 把 msg_send 的 SQLite 写入从"每条事务"改为"批量合并 + 单 writer goroutine"，
  在 durability 语义明确的前提下前移 ACK。
- 验收：S-2（1000×50）从 16.38% 提升到中间目标 ≥60%（用 CI 压测实测，不伪造）。

### 后续（不在 2.0 首发，按审计结果再立项）
- V2-2 热库分片（conv_id hash → K 库）：需改 store 接口，风险高，单独小版本。
- V2-3 会话 Actor + 普遍拉取完成态：动核心投递，单独小版本。
- V2-4 冷热分层：延续 OPS-1 未完成项。

## 审计先行（本路线的前置）
两个只读 Agent 并行审计，回来后锁定实现切口：
1. 写入路径审计：msg_send → ACK 全链路，找真实瓶颈点、group commit/WAL 真相、最小改造面。
2. 容量契约与分片审计：限流现状（超限是否显式）、分片最小切口、跨分片查询可行性。

## 纪律
- 不违反客观规律：不通过改门槛/改测试条件/伪造数据达标；压测数字全部来自 CI。
- 每阶段独立 tag（v2.0.0-beta.1 / beta.2 / v2.0.0），CI 绿 + 压测有真实改善才进下一步。
- 守住的语义：seq 单调、dedup 幂等、durability 等级明示、ACK 不撒谎（前移后崩溃窗口要明确）。
- Agent 只读审计阶段不改文件；实现阶段文件域隔离，不 commit/push/tag；主会话统一提交。
- 不引入 Docker；不走 LAGGING/RESYNC 已证伪路线；不重打历史 tag。
