# OpenDiscord v2.0 架构重设规划（草案）

状态：draft · 日期：2026-11-18 · 触发：v1.4.0 知情发布后的容量门槛缺口
依据：`docs/lts-1.4-plan.md §9` 首轮验收数据、`docs/perf-postmortem-v1.2-draft.md`、
`docs/v3-bus-design.md`、`docs/universal-pull-spec.md`

## 0. 为什么要重设（客观规律，不回避）

v1.4 首轮双规格压测（raw ceiling 无节流）4c16g 实测：

| 场景 | 实测 | 门槛 | 缺口 |
|---|---|---|---|
| S-3（512×10 人群） | 93.86% | 94.5% | 0.64%（可挤） |
| S-2（1000×50 人群） | 16.38%（带限流 36.77%） | 90% | 数量级 |
| S-1（500 人群×1000 在线） | 0.93% | 95% | 数量级 |

瓶颈已用分解证据定位：**presence/receipt/typing 全部 100% 成功，唯 `msg_send` 崩**。
S-1 负载 = ~6933 msg/s × 500 成员扇出 ≈ 346 万帧/s 下行 + 6933 次/s SQLite 提交。
这不是"调 batch/加 goroutine"能补的——是 **单进程 + SQLite 同步写入 + 全量扇出**
架构在 2c2g/4c16g 包络内的物理天花板。带生产限流削掉 97% 流量后 S-2 仍仅 36.77%，
确认是吞吐上限而非延迟 bug。

**原则**：不违反客观规律。要么减少每消息的物理工作量，要么把工作量摊到多机/多层，
要么承认某些负载不属于本系统包络并显式流控。不通过改门槛、改测试条件、伪造数据达标。

## 1. 重设目标（可量化）

| 目标 | 当前 | v2.0 目标 | 手段 |
|---|---|---|---|
| S-1 500 人群×1000 | 0.93% | ≥95% @ 4c16g | 扇出从 O(N) 降到 O(1) × 客户端拉取 |
| S-2 1000×50 | 16.38% | ≥90% @ 4c16g | 写路径异步化 + 批量提交 |
| 单机稳态吞吐 | ~3500 msg/s | ≥20000 msg/s | WAL 批量 + 分片 |
| 大群帧扇出 | 500 帧/消息 | ≤1 水位线/批 | 普遍拉取深化（v1.4 已铺路） |

关键认识：**v1.4 的普遍拉取已把"下行帧扇出"从 O(N) 降到 O(batch)**
（watermark 有 batch=50 节流），但 `msg_send` ACK 仍崩——说明 v1.4 只解决了
下行扇出的一半，**上行写入路径（每条消息落 SQLite + group commit）没动**。
v2.0 的核心是补上这一半。

## 2. 架构重设方向（按收益/风险排序）

### 方向 A：写入路径异步化 + 批量提交（最高收益，中风险）

现状：每条 `msg_send` → dedup → seqalloc → group-commit → 落库 → ACK。
group-commit 已经是批处理，但提交频率仍受消息到达速率驱动，SQLite 单写者锁竞争。

重设：
- **写前日志（WAL）+ 追加批**：把消息追加到内存环形缓冲，单个 writer goroutine
  按"满 N 条或满 T ms"批量 `INSERT ... VALUES (...),(...),...`（一次事务写 N 条），
  ACK 在入缓冲后即可返回（ack 语义从"已落库"调整为"已进入持久化队列"，需明确 durability 等级）。
- **分片热库**：按 `conv_id` 哈希到 K 个 SQLite 文件（K=CPU 核数），多写者并行；
  跨分片查询走聚合层。这直接把写吞吐提升 K 倍。
- **风险**：ACK 语义变化需客户端/协议确认；崩溃窗口内未落库消息的恢复（WAL replay）。

### 方向 B：会话级消息总线 + 订阅广播（高收益，高风险，动核心）

现状：flusher 每条消息调 `ListMembers` + 逐成员 fanout（即使普遍拉取也要按 uid 分流）。

重设：
- 每个活跃会话一个 **会话 Actor**（单一 goroutine 拥有 seq 分配 + 成员表 + 水位线状态），
  消息进 Actor 队列串行处理，消除跨 goroutine 锁竞争。
- 下行从"逐成员 push"彻底改为"会话水位线 + 客户端批量拉取"（v1.4 universal pull 的完成态），
  服务端只维护每会话一个 latestSeq，成员连接订阅该会话的水位线广播。
- 慢消费者不下行推送任何数据帧（v1.2 教训：LAGGING 降级失败因依赖不存在的客户端行为），
  完全由客户端按 seq 主动拉，天然免疫慢消费者。
- **风险**：客户端拉取调度器的成熟度（v1.4 已实现 pull-scheduler，需验证大群收敛延迟）；
  Actor 模型的会话迁移/恢复。

### 方向 C：冷热分层与卸载（中收益，低风险）

- 冷数据（>N 天）迁 PostgreSQL/对象存储，热库只留活跃窗口（现状已有 pg adapter 骨架）。
- 媒体/缩略图/波形走独立对象存储，不占消息库 IO。
- 这是 v1.4 OPS-1 未完成项的延续，可作为独立批次先做。

### 方向 D：显式容量契约（必须做，非优化）

- 承认单进程 SQLite 架构有天花板：定义每规格的**准入容量**（如 2c2g 最大 512 并发/10 人群，
  4c16g 最大 1000 并发/50 人群），超限请求由限流层**显式拒绝**（kind 13 RATE_LIMITED），
  不再让 msg_send 静默超时。
- 压测门槛改成"在准入容量内 ≥95%"，超出容量返回明确限流响应——这才是遵守客观规律的做法。
- 这需要产品侧决策：是"承诺无限容量"还是"承诺容量内 SLA + 超限显式降级"。

## 3. 分阶段路线（每阶段 CI + 压测守门）

| 阶段 | 内容 | 门槛 | 风险 |
|---|---|---|---|
| V2-0 | 容量契约定义 + 显式限流（方向 D） | 准入容量内不超时、超限有 kind13 | 低 |
| V2-1 | 写入批量化 + WAL（方向 A 第一步） | S-2 ≥60%（中间目标） | 中 |
| V2-2 | 热库分片（方向 A 第二步） | S-2 ≥90% | 中 |
| V2-3 | 会话 Actor + 普遍拉取完成态（方向 B） | S-1 ≥95% | 高 |
| V2-4 | 冷热分层（方向 C） | 冷库查询延迟达标 | 低 |

每阶段独立 tag/Release，不捆绑。

## 4. 不做什么（同样重要）

- 不重打 v1.2.1 历史 tag 修 S-7 基线（历史就是历史）。
- 不追求"无限容量"——单进程有物理上限，靠分片/多机而非硬扛。
- 不引入 Docker（用户原始架构约束：无容器部署）。
- 不再走 LAGGING/RESYNC 降级路线（v1.2 已证伪，见 perf-postmortem）。

## 5. 立即可做的下一步

1. 产品侧定"容量契约"口径（方向 D），这是所有后续工作的前提——
   它决定了 S-1/S-2 是"必须达标"还是"不属于准入容量"。
2. 重跑 S-4/S-5/S-6 让工具 bug 修复生效（不改变发版结论，只补全数据）。
3. 针对 S-3 的 0.64% 做 3 次重复测量，确认是抖动还是稳定缺口（若稳定，约 1% 的优化即可闭合）。
4. 方向 A 的 PoC：在单会话上验证批量 INSERT 的吞吐提升，用 CI 压测量化。
