# OpenDiscord 路线图

> 状态以代码与 `docs/lts-checklist.md` / `CHANGELOG.md` 为准。本文件只列方向与判据，不承诺日期。

## 已完成

### v1.0 — 可部署的骨架
分层 socket 架构（总线/桥接/用户/管理/数据五层）、SQLite 热库 + Postgres 冷库分域设计、
管理 REST + TUI 后台、认证全套、单二进制内嵌双 SPA、systemd + Caddy 部署件。

### v1.1（LTS 基线）— 把设计变成可用的产品
- 消息闭环：已读/送达回执、输入中、在线状态、成员变更通知、消息撤回
- 媒体：客户端生成缩略图与波形（服务端不需要 ffmpeg）、缩略图落文件系统 + 配额
- 通话：WebRTC 1v1 语音/视频，服务端只转发信令、媒体流 P2P
- 交互：CLI/TUI 双模式、中英双语、`opchat` 纯 TUI 管理台、管理后台 Dashboard
- 工程：全平台构建矩阵（5 架构 × 2 平台）、压测工具、文档自动校验（doccheck）
- 可靠性：热库真实收缩（归档删除 + trim + GC）、广播异步扇出 + 聚合、
  成员缓存、群人数上限、审计覆盖破坏性操作

### v1.2（LTS）— 拉取模式与稳定性
- 大群拉取模式：kind 14 水位线 + 客户端 pull-scheduler（singleflight + jitter），
  500 人群下行帧需求 ~1M/s → ~2k/s；202 快照 `members_omitted` 防 64KB 帧上限
- 两轮性能负优化（假合批 / LAGGING 降级 / 无锁扇出）压测证伪并全部回滚，
  教训制度化（`docs/perf-postmortem-v1.2-draft.md`）
- 项目更名 OpenDiscord；v3 总线 P0~P3d-1 代码落盘（默认关闭零行为影响）

### v1.4（LTS，进行中）— 普遍拉取 + 自适应 + v3 总线
按 `docs/lts-1.4-plan.md` §5 的 12 条决策执行，全部 flag-off 待 S-1~S-7 验收：
- 机制在位：普遍拉取分流、AIMD 自适应控制器、v3 hub/plane/双写旁路、
  106/109/@/453 消息域、PWA+Web Push 前端、供应商 webhook 适配器、
  `chatd-pg` 变体、`opendiscordctl upgrade`、TURN 自检、会话列表虚拟滚动
- 未完成（发布前必须闭环）：CORE-3 接线四项（钩子注册 / 灰度关旧直投 /
  kind 15 上行 / 背压上报）、自适应控制循环接线、Web Push 服务端、
  全量灰度与默认值调整（群上限 100 → 1000 待压测达标）

## 下一版（v1.5 候选）

按"不修就会出事"的优先级排序。

### 1. 冷库真正可用（生产准入）

**为什么**：`cold_dsn` 需部署层注册 driver；未注册时审计只写日志不落盘、
历史搜索退化为只搜热库 90 天。合规部署要求审计可追溯数年，这项目前做不到。

**怎么做**：把 pgx 驱动注册进装配（`server/cmd/chatd`），冷库不可用时按
`require_audit_store` 显式拒启（已有开关，只是驱动没接）。

**判据**：配好 `cold_dsn` 后 `opendiscordctl doctor` 的 `audit_store` 为 OK；
撤回/成员变更/通话的审计事件能在冷库 `sys.audit_log` 里按 since_id 翻到；
`GET /api/v1/audit` 返回真实数据而非降级日志。

### 2. 供应商接入（生产准入）—— 已于 v1.4 落地适配器缝

v1.4 已提供通用 HTTP webhook 适配器与示例配置（`deploy/providers.example.toml`），
生产接入 = 指向真实供应商 webhook 后验证。以下判据不变：

**为什么**：短信/邮件/图形验证码只有接口缝，生产环境注册登录不可用。

**怎么做**：`SMSSender` / `Mailer` / `CaptchaVerifier` 三个接口各实现一个供应商适配器
（国内短信建议阿里云或腾讯云，图形码建议极验或腾讯防水墙），配置驱动选择。

**判据**：生产配置下真实手机号能收到验证码并登录；邮箱能收到魔法链接；
第 2 条 OTP 起强制图形码且无法绕过。

### 3. 移动端推送 + PWA —— 前端部分已于 v1.4 落地（服务端未实现）

PWA（manifest + SW，production-only）与 VAPID 订阅封装已在位；**服务端
`/api/push/subscribe` 与 push 下发未实现**，通知仍收不到（fail-closed）。
判据不变：

**为什么**：没有推送，手机锁屏就收不到消息 —— 移动端实质上不可用。
这是与微信/QQ 差距最大的一项。

**怎么做**：PWA（manifest + service worker + 离线缓存）先让手机浏览器可"添加到主屏"；
推送走 Web Push（VAPID）或接厂商通道（FCM/APNs/国内厂商）由部署方选择。

**判据**：手机添加到主屏后能正常收发；App 在后台时收到系统通知；
点击通知直达对应会话。

### 4. 群治理

**为什么**：现在群只有"成员 + 角色"骨架，没有禁言/进群审批/群文件，
开不了真正的群。

**怎么做**：禁言（全员/单人/定时）、进群审批、邀请链接、群文件列表。
数据结构上 `conv_members.muted_until` 已有，主要是接口与 UI。

**判据**：群主可禁言某人 1 小时且该成员发消息被拒；新成员需群主批准才进群；
群文件可上传下载。

### 5. 消息体验补齐 —— 服务端已于 v1.4 落地（`msg_domain_v2_enabled` 门控，默认关）

106 编辑、109 转发、@ 提及、453 举报服务端实现在位，灰度开启后生效。判据不变：


**为什么**：@提及、引用回复、撤回 UI 都还差最后一公里（服务端与协议都在，
前端 UI 未接线）。

**判据**：长按消息能引用回复并在气泡里显示引用块；@某人后对方收到高亮提醒；
撤回按钮可用且 2 分钟后自动变灰。

## 明确不做（附理由）

| 项 | 理由 |
|---|---|
| 朋友圈 / 动态 | 那是社交产品，不是 IM 内核 |
| 支付 / 红包 | 涉及金融合规，与自托管定位冲突 |
| 公众号 / 小程序 | 生态型功能，需要平台方角色 |
| 自建 SFU 群通话 | 需要独立服务与带宽预算；1v1 通话完整，群通话留待云 SFU 集成（v1.5+ 评估） |
| split 多进程部署 | 死 systemd 单元已在 v1.4 删除；单机 2C2G 已够用，拆分留给真正需要水平扩展的部署方 |
| 端到端加密（E2EE） | 涉及密钥托管与多设备协商，需要独立设计与审计周期；
消息表已预留 `payload`/`envelope` 字段，不属于 LTS 范围 |

| 项 | 理由 |
|---|---|
