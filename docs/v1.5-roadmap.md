## 四步版本

### 步骤 1 — v1.5.0-beta.1：UX 文案重写（sota-ux-writing）
- Agent 读 `/var/minis/skills/sota-ux-writing/SKILL.md` 全部 rules，AUDIT 现有界面文案：
  - `apps/client/src/ui/i18n/zh-CN.ts` + `index.ts`（客户端文案字典）
  - 客户端 views（login/chat/conv-list/settings/call/banned）与管理端 views 的硬编码用户可见文本
  - CLI 输出消息（`server/cmd/opendiscordctl`、`adminctl`）
- 按 voice/tone + plain-language(ISO 24495-1) + 错误消息三要素（后果/原因/下一步）
  + 按钮动词化 + 术语一致性（对照 docs 用词）重写；报告 banned-string grep 结果。
- 只改文案字符串与字典，不改逻辑、不改组件结构。
- 同一 Agent 追加写 `docs/terminology-dictionary.md`（术语字典：界面/文档/API 同名同义）。

### 步骤 2 — v1.5.0-beta.2：技术文档重写（sota-docs-workflow）
- Agent 读 sota-docs-workflow SKILL，按 Diátaxis 审计并重写技术文档架构：
  - 把现有 docs/ 归入 tutorial / how-to / reference / explanation 四类，产出 `docs/README.md` 导航
  - 修 `docs/api-reference.md` / `cli-reference.md` / `ws-protocol.md` 的事实漂移（对照代码）
  - runbook：部署/备份/回滚/升级的操作手册化（deploy.md 已是 1128 行，做导航与索引整理，不删内容）
  - README 的文档链接集合与 docs/README.md 一致
- 诚实纪律：文档不承诺代码没有的机制；推送/举报未实现前不得写成已实现。

### 步骤 3 — v1.5.0-beta.3：README 重写 + 功能补齐（sota-copywriting + 功能 Agent）
- Agent A（sota-copywriting）：按 skill 重写 README.md，事实保全（版本号/基准数据/产物/链接集合一致），
  面向新用户/部署者/开发者三层，不夸大（容量缺口保留）。
- Agent B（功能）：实现两个已明确记录的功能缺口：
  1. **移动端系统推送**：服务端 `POST /api/push/subscribe`（Cookie 鉴权，body `{subscription: PushSubscriptionJSON}`，
     VAPID 配置读 env，fail-closed），Web Push 下发（新消息触发），与前端 `apps/client/src/net/push/index.ts` 对接。
  2. **举报链路**：服务端 453 REPORT 上行路由（pipe.dispatch）+ 入库（audit 冷库或 hot reports 表），
     前端 MessageList 举报占位接线（替换 `t('chat.n')` 占位为真实入口）。
- 两者都必须 CI 全绿（go test -race + web build + kinds 一致性），本地不跑测试（可 gofmt/读）。

- 若 riscv64 再次偶发卡死：按 v1.4 经验删 tag 重打重推（tag 重建安全，Release 未创建前）。

## 纪律
- 每步独立 tag（beta.1/2/3 → 正式 v1.5.0），每步 CI 绿才进下一步；不在 CI 未绿时报告完成。
- Agent 只做分配的文件域，不跨步改文件；skill 全文由 Agent 自行 file_read。
- 文案/文档/功能三类修改互不冲突（不同文件域）；Agent 不 commit/push/tag，由主会话统一提交推送。
- 版本号顺序：v1.5.0-beta.1 / beta.2 / beta.3 / v1.5.0。
- 用户铁律：不本地跑 go test/build（可 gofmt -l / curl / git）；CI 等待用 minis-scheduled 定时器。
